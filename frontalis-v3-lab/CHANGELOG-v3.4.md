### SPEC の曖昧さ・矛盾と、Stage 1 での読み（黙って選ばずに記録する）

SPEC は凍結済みなので変えていない。以下は、実装で選ばざるをえなかった読みである。どれも `ra_protocol.py` / `make_histories_v34.py` の hash に含まれる（Stage 4 までに変えるなら、理由と前後の結果を本ファイルに追記する）。

- **A1（矛盾に近い。影響が大きい）入れ替えの「特徴の名前の並びが完全に一致」（第 6 節）。** 条件づけ C の手がかり（`type:<結果の型>` など）は、BG ごとに登録される結果の型が違うので、並びも集合も
  BG の間で一致しない（開発用の種で確認: ERR-interp・SRC-none の BG 全 3 組で、`type:support` などが片方にしかない。SRC-reliable では集合は同じだが並びが違う）。文面どおりに C の並びまで求めると、
  BG の組はすべて除かれ、val-swap（RA2。W・Σ・a・C を入れ替える）は全個体で「判定できない」になる。Stage 1 の `aligned()` は、価値ネットの特徴（人モデル・状況モデル）の名前と並び、
  経験記録の id の並びの一致を求め、C は 1 つの対象として丸ごと入れ替える（元の人格にない手がかりは 0 と読む）。文面どおりの読み（`aligned_literal()`）も実装してあり、除かれる数の報告に使える。
  開発用の種ではどの BG の組でも、価値ネットの特徴の並びは一致した。**この読みを Stage 5 で使うか、文面どおりに全個体を除くかは、リードの判断を要する。**
- **A2 BG の書式。** 「{credit_shared, Pk, m1}、{support, Pk, m2}」の「、」は同じ経験の 2 つの結果と読み（MIS の「・」と同じ意味）、相手 Pk（k = 1..12）ごとに 1 経験、計 12 経験とした。
  順序は種で並べ替え、m1・m2 は経験ごとに引く。3 つの BG は同じ並べ替えと同じ m1・m2 を使う（BG の違いが型の構造だけになる）。
- **A3 SRC の書式。** 「(3)(4) Qk との直接の経験 2 回」は、2 回とも同じ型の結果を持ち、m′ は経験ごとに引くと読んだ。SRC-none は、4 エピソードそれぞれで「独りの練習、空の刻み、独りの練習 2 回」（経験 12 + 刻み 4）。
- **A4 訂正されない誤帰属 M 本（確信の変種）の対照。** 「MIS を最初から真実の結果にした」対照には、M 本を含めず、誤帰属の人格と同じ（誤った）M 本を足した。対照との差は、訂正した N 本だけから生じる。
- **A5 空の刻み（`advance_clock`）。** SPEC は「訂正なしの枝: 時計を N 進めるだけの空の刻み」を置くが、v3.3 の `npnv3/` には存在しない（Stage 2 で加わる）。
  Stage 1 の条件（C-v33、C-nocorr、C-retro、C-none、diag-q0）はどれも「訂正は時計を進めない」（v3.3 の T.2）なので、訂正なしの枝では何もせず、SRC-none の刻みも無視する。
  v34 の条件では `advance_clock` が要る（現在は `NotImplementedError`）。
- **A6 RC1〜RC3 の量の定義。** 第 3 節は「傾き」「訂正の予測空間の利得の和」「共有の特徴に乗る」「動く」の定義を持たない。診断用の種の結果を見る前に、`tests/diagnostics_v34_rc.py` の冒頭に定義を書いた
  （下の「RC の定義」に同じものを写す）。
- **A7 読み出しの細部。** r6・r7・r9 は、v3.3 の `AMBIGUOUS_A` と同じ形（参加者はその相手だけ、credit_taken 0.5 / credit_shared 0.5、大きさ 0.8、`appraise`。状態は変わらないことを確認）。
  r8 は状況プローブ（participants = A と O）の Q。r3 の O の類は ERR-report-x で mentor。正規化の標準偏差は ddof = 1。
- **A8 語彙。** 類 `peer`、文脈 `review`、概念 `joint_work` は `data/lexicon.json` にない。v3.1 の規則（未知語はゼロベクトルで登録し警告）に従う。`collaborator`・`mentor`・`studio`・`workshop` などは既知。
- **A9 hm-eq の意味。** 訂正の学習は経験記録の `h_before` を使い、気分は読み出しにしか入らない（v3.3）ので、C-v33 の上の hm-eq では R_cor がビット単位で変わらない（開発用の種で確認）。
  hm-eq が効きうるのは訂正の後の FOL だけで、RA2-hm の意味は C-v34（M3 で気分と h が τ を通る）が入った後に決まる。報告として残す。

### RC の定義（診断用の種 3460〜3479 を実行する前に固定。2026-10-16）

`tests/diagnostics_v34_rc.py` の冒頭と同じ。r(N) = N ごとに全セル（M・BG・ERR）と全種をまとめた「平均どうしの比」mean(d_post)/mean(d_pre)。
RC1 = (i) r(N) の傾き（5 つの N）が diag-q0 では C-v33 の 50% 以下（絶対値）、かつ (ii) diag-q0 の r(16) ≥ 0。
RC2 = 訂正ごとの利得（含意された変化の絶対値で重み付けた予測空間の利得）の、個体ごとの和の N ごとの平均と、1 − r(N) の Pearson 相関（5 点）≥ 0.9。
RC3 = 好悪の変化 Δlike(A) の層（ind と共有 = people + cls + emb）への分解で共有の割合（符号つき、個体をまとめた比）≥ 0.30、かつ A2 の好悪の変化の平均が Δlike(A) の平均と同じ符号で、
90% 以上の個体で |Δlike(A2)| > 1e-6。

### 実行環境による逸脱

- **E1 `tests/helpers.py` の `pmap` は `fork` を使う。Windows に `fork` はない。** H6 の作業用の写し（リポジトリ外）では `pmap` を直列にし（結果は種ごとの計算で決定的なので値は変わらない）、
  テストのモジュールごとに別のプロセスで走らせた。リポジトリ内の `tests/helpers.py` は変えていない。新しい `tests/ra_protocol.py` は spawn のプロセス並列（`ProcessPoolExecutor`）を使う。
- **E2 作業中に、`taskkill /F /IM python.exe` を 1 度実行し、その時点の全 python.exe を終了させた**（H6 の最初の実行が `fork` の欠如で全 B 系テストを ERROR にしていたのを止めるつもりだった）。
  同じ機械の他のセッションの python が巻き込まれた可能性がある。以後は自分が起動したプロセスだけを扱った。
