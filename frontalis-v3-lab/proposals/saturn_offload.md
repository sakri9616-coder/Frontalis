## 1. 退避に向く作業・向かない作業

| 区分 | 作業 | 理由・注意 |
| --- | --- | --- |
| 向く | 開発用の種での本番規模の確認（`p15_prod.py cells ...`） | 1 区画 1〜2 時間。チェックポイントから自動で再開する |
| 向く | リハーサル（`p17_rehearsal.py <学習器> lr`） | 種 77340〜77342 だけを使う |
| 向く | κ の確認（`p14_kappa_check.py`）、規模の曲線、学習率の選び直し（`p15_prod.py lr <値>`、`p16_nn_learnability.py <変種>`） | 判定の量を使わない調整 |
| 向く | メモリの制約で分けていた区画（例: NN-REL の本番規模、720 人格を 1 本で走らせる区画） | VRAM の大きい GPU なら分けずに済む見込み（第 6 節）。分けても分けなくても結果は同じ（人格ごとの乱数の流れが独立なので）。ただし、これは要確認（同じ種の区画を 2 通りに分けて比べる） |
| 注意 | **評価用の種 77100〜77139** | 1 回限り。**評価の本番は 1 か所でだけ実行する**（区画を手元とクラウドに分けない）。クラウドで行うなら、その前に、クラウドで開発用の種を通し、第 4 節の検査で手元との同等性を確かめる |
| 向かない | bf16 の使用 | 草案 3.1 第 10b 節の検査に不合格（P12）。クラウドでも fp32 のまま |
| 向かない | 認証情報を要する作業（push など）の自動化 | 認証情報はユーザーが設定する。第 5 節 |

## 3. 実行のしかた（中断に強く）

- **チェックポイントの置き場所**: コードは Python の `tempfile.gettempdir()` の下に書く（`v4d_ckpt_p15/`、`p17_ckpt/`）。クラウドの `/tmp` は停止で消える可能性があるので、**起動の前に `TMPDIR` を永続する場所に向ける**（要確認: Saturn で再起動の後も残る場所。ホームの下が残るかを確かめる）。チェックポイントは 1 個で最大約 0.9 GB（240 人格）。
- **待ち行列**: `queue_cloud.sh`（`queue4.sh` と同じ形。インタプリタは `$PY`、終わった行は `queue_cloud.done` に書いて、再起動の後は飛ばす）。

```bash
cd ~/Frontalis/frontalis-v3-lab/proposals/probes
export TMPDIR=$HOME/v4d_tmp && mkdir -p $TMPDIR      # 要確認: 永続する場所
cp queue_cloud.example.txt queue_cloud.txt          # 中身を編集する（例は第 1 節の向く作業だけ）
PY=$HOME/v4d_venv/bin/python nohup bash queue_cloud.sh queue_cloud.txt > /dev/null 2>&1 &
tail -f queue_cloud.log                             # 進み具合。誤りは queue_cloud_jobs.err
```

- **再開**: 止まった後は、同じ `TMPDIR` で同じ待ち行列をもう一度起動する。終わった行は飛ばされ、途中の区画（`p15_prod.py cells`、`p17_rehearsal.py`）は、`cells.run_cell` が構成のハッシュつきのチェックポイントから再開する（再開がビット一致することは P13・`p13_ckpt_early.json` で確認済み。最後のチェックポイントは 28,000 経験なので、最大で 4,000 経験＋測定をやり直す）。チェックポイントを持たない作業（`p14_kappa_check.py`、`p16_nn_learnability.py`、`p18`〜`p21`）は最初からやり直す。
- **自動の停止**: 要確認: Saturn の資源の自動停止（無操作で止まる設定）の有無と時間。長い区画の途中で止まっても上の手順で再開できるが、測定の段の途中で止まると、測定をやり直す。課金は資源が動いている間ずっと続く（第 7 節）。
- 1 つの GPU で同時に走らせるのは 1 本だけ（手元の方針。複数を同時に走らせると、手元では VRAM が足りなくなった）。大きい GPU で並行させる場合は、第 6 節の測定の後に決める。

## 4. 手元とクラウドの結果の同等性の検査（結果を見る前に定義する）

浮動小数点の演算の順序が GPU ごとに違うので、ビット一致は期待しない。さらに P18 で、ミニバッチの順だけを変えた再試行が評価の距離の大部分を作ることが分かっている。小さな数値の違いも SGD の経路に沿って育ち、「同じ条件の再試行」と同じくらい違う結果になる可能性が高い。そこで、bf16 の検査（草案 3.1 第 10b 節）と同じ形で、**2 段の同等性**を、クラウドの結果を見る前に `p21_cloud_equiv.py` に固定した。

- 実行: リハーサルの種 77340〜77342、NN-SET、I-H、C-off と C-SLp、F1・F6m・F5、役 6、2,000 経験、S/N 1、学習率 1e-3。手元の基準は `p21_local_rtx3050.json`（commit 済み）。クラウドで `run cloud` と `run cloud_retest retest`（環境と SGD の乱数の流れだけを +1000 ずらした、同じ条件の再試行）を走らせ、`compare local_rtx3050 cloud cloud_retest`。
- 量 m: D_AB、D_AA′、ρ の距離（P_un・P_nc）、入れ替えの距離、特徴の交差予測、R²_un・R²_nc、再現性の相関。世界ごとに δ_m = |m_クラウド − m_手元|、ν_m = |m_クラウド − m_クラウドの再試行|。
- **段 1（数値として同等）**: E1 すべての m で δ の中央値 ≤ 0.2 × ν の中央値。E2 すべての m で δ の 90 百分位 ≤ 0.5 × ν の中央値。E3 非有限 0。E4 クラウドで `p13_ckpt_early.py` が identical: True。
- **段 2（再試行として同等）**: E5 すべての m で δ の中央値 ≤ 1.5 × ν の中央値、かつ E3・E4。
- 使い方（事前に固定）:
  - 段 1 に通る: クラウドと手元の区画を、同じ判定の中で混ぜてよい（開発用の種に限る）。
  - 段 2 だけに通る: クラウドの結果は開発の証拠として使ってよいが、同じ判定の中で手元の区画と混ぜない（区画の一覧に機械を書く。`cells.run_cell` は `meta` に GPU の名前・torch の版・ホスト名を書く）。評価の本番をクラウドで行うことは許す（全区画をクラウドで行う場合に限る）。
  - 段 2 にも通らない: 原因（乱数の列の違い、ライブラリの版）を調べる。それまでクラウドの結果は報告だけに使い、判断に使わない。評価の本番はクラウドで行わない。
- 手元での自己検査（`p21_compare_selftest_local.json`）: 手元の 2 回の実行は δ = 0 で、段 1・段 2 とも通った（比較の計算が動くことの確認だけ）。手元の ν の中央値は、D_AB 0.026、D_AA′ 0.016、R²_nc 0.041 など。

## 5. 結果の持ち帰り

- 結果のファイル名は、スクリプトが決めた名前のまま（`p15_cells_<学習器>_<生得>.json`、`p17_cells_lr.json` など）。クラウドの結果は**別のブランチ**に置き、手元の結果と同じブランチで上書きしない。名前の例: `claude/value-representation-design-cloud-a10g-20261018`（GPU と日付）。手元の結果との差は `git diff` で見る。
- 持ち帰りの方法は 2 つ。どちらにするかはユーザーが決める。
  1. クラウドから、上の別のブランチに commit して push する。**GitHub の認証（トークンなど）はユーザーが設定する**（要確認: Saturn の秘密の値の機能で、環境変数として渡す方法）。
  2. Jupyter の画面からファイルをダウンロードする（認証は要らない）。
- **鍵・トークン・パスワードを commit しない**。commit の前に `git status` と `git diff --cached --stat` で、`.json`・`.txt`・`.log`・`.py` だけであることを確かめる。チェックポイント（`.pt`、約 0.9 GB）は `TMPDIR` に置き、リポジトリに入れない。
- 評価用の種の結果がクラウドで出た場合は、push の前にリーダーへ先に報告する（リーダーの指示）。

## 6. GPU の種類ごとのメモリの見込みと、最初の 1 時間で測る項目

メモリは 2 種類を分けて扱う（`DESIGN.md` 第 10.1 節）。

- **GPU の VRAM**: 手元の実測（P20、`p20_mem.json`、本番の構成 32,000 経験・S/N 4、**学習の段だけ**）: NN-SET 約 2.1 MiB／人格（＋固定 約 130 MiB）、NN-REL 約 9.1、KRR 約 7.5、RF 約 4.2、HB 約 5.3 MiB／人格。測定の段（評価の状態の入れ替え、特徴の交差予測）の最大値は未測定（要測定）。
- **ホストの RAM**: 手元の失敗はこちら（本番規模 720 人格で、乱数の列 11.0 GiB の `np.stack` が確保できなかった。今のコードは 1,000 経験ごとに作るので、240 人格で区画ひとつ約 123 MB）。チェックポイントを書くときに、1 個ぶん（240 人格で約 0.9 GB）をホストで組み立てる。測定の段のホストの RAM の最大値は未測定（要測定）。

| GPU（Saturn の例） | VRAM（NVIDIA の公表値） | 学習の段だけから見た人格数の上限（VRAM の 8 割、NN-SET / NN-REL / KRR） | 今の区画（240〜432 人格）を分ける要否 | ホストの RAM（Saturn の表） |
| --- | --- | --- | --- | --- |
| T4 | 16 GB | 約 6,000 / 1,400 / 1,700 | 不要の見込み | T4-XLarge 16 GB、T4-4XLarge 64 GB |
| A10G | 24 GB | 約 9,000 / 2,100 / 2,600 | 不要の見込み | G5XLarge 16 GB、G52XLarge 32 GB |
| V100 | 16 GB（AWS p3 は 16 GB、要確認） | 約 6,000 / 1,400 / 1,700 | 不要の見込み | V100-2XLarge 61 GB |
| H100 | 80 GB | 約 30,000 / 7,000 / 8,500 | 不要 | 1xH100 200 GB |

上限は学習の段の線形の外挿で、測定の段を含まない。**ホストの RAM が 16 GB の型は避ける**（手元の 32 GB でも、古いコードでは足りなかった。今のコードの必要量は要測定）。

最初の 1 時間で測る項目（`queue_cloud.example.txt` の段 A）:
1. `p13_ckpt_early.py`（決定性と再開）。
2. `p20_mem.py`（VRAM の人格あたりの量。手元の値と比べる）。
3. `p21_cloud_equiv.py` の 3 行（同等性。所要時間が、NN-SET のリハーサルの規模の速度になる。手元は 108 人格 × 2,000 経験で約 5〜7 分、GPU は共有）。
4. 1 区画の本番規模（例: `p15_prod.py cells set IH C-S0`）の最初のチェックポイント（4,000 経験）までの時間。手元は 240 人格で 10〜28 分（他の処理との共有で変動）。
5. その間の `nvidia-smi` の VRAM と使用率、ホストの RAM（`free -h`。要確認: 使えるか）の最大値。
