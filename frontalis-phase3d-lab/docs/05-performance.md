# Phase 3-D：CPU・GPU・保存移植の実測

100,014パラメータまで、現在の評価ツールはCPU単独で実用的な応答時間を保った。1件の評価の中央値は0.63～1.75ms、1経験の更新は12.5～33.8msだった。この小さな入力とバッチでは、GPUへ移してもツール全体は高速化しなかった。GPU利用そのものには成功した。

これは性能測定であり、大きい人格のほうが優れているという結果ではない。人格形成の比較は `04-numeric.md` と数値実験の記録で別に判定する。

## 測定条件と証拠

- 原記録：`reports/performance.json`、環境：`reports/runtime.json`。測定全体74.35秒。2026-10-15のローカル実行。
- Windows 11、Ryzen 5 3600、RTX 3050 8GB。新ラボ専用Python 3.12.13、Torch 2.7.0+cu128、CUDA 12.8、NumPy 2.5.4。CPUスレッド数1。
- raw8、同じ初期seed4311、同じ系列0の事実16経験、`bounded_signal`。隠れ幅16／64／312／3125。100万規模は割り当てていない。
- CPU float64／GPU float64／GPU float32を別条件として計測。GPU条件の学習・評価テンソルの実デバイスは全て`cuda:0`だった。
- 1件評価は暖機10回の後200回、96件バッチは暖機10回の後100回。表は中央値／95パーセンタイル。入力の検証、数値安定性検査、NPNの出力生成、CPUへ見える配列への変換を含むAPIの時間。LLMへの通信・文章生成は含まない。
- GPUは各試行の前後で同期した。非同期の処理発行だけを測った値ではない。
- 更新は同じ16経験後の状態を複製し、同じ17番目の経験を5回別々に追加。複製の時間を除き、内的評価、再学習8epoch、状態・履歴更新を含む。更新回数を重ねて異なる人格になった5状態の平均ではない。
- 通常のデスクトップを使った1回の測定であり、PC・GPUを専有していない。小さな差や下位3容量の速度順は優劣と解釈しない。p95も独立反復実験の信頼区間ではない。

固定係数の数値部分はさらに448 bytes。表の重みサイズにPythonオブジェクト、経験文、再学習用記録、Adamの作業用配列、Torch本体は含まない。最初の526版の初期化にはTorchの初回演算の準備が含まれる。他のモデルより初期化が遅いからといって小容量特有の欠陥とはいえない。Pythonの起動・Torchのimportの待ち時間はこの「初期化」には含まない。

## RAMとVRAMを混同しない

CPU NN測定中のプロセスRAM（RSS）は約543～560MiB。これはTorch等を含むプロセス全体であり、100,014の重みだけが560MiBあるわけではない。GPU測定に進んだ後のRSSは約876～1,020MiBとなった。CPU→GPU→単純方式を同じプロセス内で順に測ったため、WindowsのピークRSSはプロセス開始からの累積値で、後の単純方式にもGPUランタイム等の残ったメモリが含まれる。方式別の専有RAM比較には使わない。元JSONには各測定の前・初期化後・16経験後・最後のRSS、Windowsのピーク作業セット、private bytesを保存した。

| 学習数 | GPU float64：PyTorch最大確保／最大予約MiB | GPU float32：PyTorch最大確保／最大予約MiB |
|---:|---:|---:|
| 526 | 16.30／22.00 | 16.28／22.00 |
| 2,062 | 16.37／22.00 | 16.32／22.00 |
| 9,998 | 16.80／22.00 | 16.53／22.00 |
| 100,014 | 21.60／46.00 | 18.93／24.00 |

VRAMは各モデル直前にPyTorchのピークをリセットした。更新用の複製やAdamの一時配列、PyTorchの作業領域を含む。CUDAコンテキスト・ドライバ等が使う全VRAMを網羅する数値ではない。[PyTorchのメモリ計測API](https://docs.pytorch.org/docs/stable/torch_cuda_memory)の確保量と予約量を別々に記録している。

`nvidia-smi`が示したGPU全体の使用量は計測前1,836MiB、計測末尾4,080MiB。その後に計測プロセスが終了してから読んだ値も4,002MiBだった（`reports/performance-postprocess.json`）。他アプリとデスクトップの利用を含むため、差分の2,244MiBをNPNの消費量とは帰属させない。GPU上のモデル重み、PyTorchアロケータ、デバイス全体の使用量は別の測定対象である。

## GPU→CPU保存復元と、精度・環境を変えた再学習

同じ16経験をCPUとGPUで別々に学習する試験と、同じGPU重みを保存してCPUへそのまま移す試験を分けた。

| 学習数 | CPU64／GPU64の別学習：最大出力差 | GPU64／GPU32の別学習：最大出力差 | 同じGPU64重みをCPUへ復元：最大出力差 |
|---:|---:|---:|---:|
| 526 | 1.62e-14 | 1.30e-6 | 1.94e-16 |
| 2,062 | 4.68e-12 | 0.0460 | 2.50e-16 |
| 9,998 | 7.90e-10 | 0.00258 | 7.22e-16 |
| 100,014 | 3.79e-12 | 0.000441 | 2.33e-15 |

GPU64→CPU64の保存復元では、全容量でパラメータハッシュが一致した。96件×7尺度の評価差も丸め誤差程度だった。一方、CPU64とGPU64の**別々の再学習**ではハッシュは一致しない。数値は近くてもビット単位で同一という証明にはならない。

float32で別に学習すると2,062モデルで最大0.046の差があった。精度が違う学習を、同じ人格状態の移植と扱ってはいけない。既存評価を次の教師に使う循環では、計算精度の差も次の学習に入る。今回の測定だけで差の詳細な増幅機序を特定したとはいえないが、float32への置換が無影響ともいえない。主比較をCPU float64に統一し、保存済みのfloat64状態を正本として保持する。

既存CPUランタイムTorch 2.14.1+cpuと新環境2.7.0+cu128をCPU float64・1スレッド・同じ16経験で比較したところ、最大出力差は526版2.31e-14、2,062版9.61e-12だった。既存ランタイムにpsutil等を追加していない。これも16経験時点の確認であり、1,000経験の長期軌道まで一致すると拡張して解釈しない。

## 再現方法

新ラボ内のPowerShellで実行する。既存記録は上書きしない。再計測は新しい名前を指定する。

```powershell
$env:PYTHONUTF8 = '1'
$env:PYTHONDONTWRITEBYTECODE = '1'
& '.\.venv\Scripts\python.exe' experiments/performance.py --output-tag performance-rerun-1
& '.\.venv\Scripts\python.exe' -m unittest discover -s tests -p test_performance.py -v
```

再計測は性能を確かめるための追加ランになる。主実験の人格状態や数値比較の結果を書き換えない。テストはタイマー同期、単位、数値部分のbytes、記録の実デバイス・有限性、保存復元の一致、100万規模の禁止、旧ランタイムに依存を追加しない動作、再計測の出力先を検証する。

主測定の100kまででは、通常の1件判断をGPUに移す必要性は示されなかった。大容量・大バッチでGPUが有利になる可能性を否定する結果でもない。100万規模は数値実験の事前ゲートを満たした場合に限り、別の条件として検証する。

## 条件付き追加：1,000,014パラメータ

上記の主測定の後、検証データの容量ゲートが成立し、`01b-million-protocol.md`を固定してから追加測定を行った。ゲートの25.6007%改善は近似診断の検証値であり、人格の良さを決める指標ではない。この追加結果で主15条件の記録を置き換えていない。`reports/million-performance.json`と`million-performance-runtime.json`へ別保存し、主`performance.json`／`runtime.json`が測定前後で同じハッシュだったことを記録した。

raw8・幅31,250・学習1,000,014、1経験の更新対象500,007、別途固定56個。seed4311・系列0・同じ16事実・信号損失・CPU1スレッド。測定回数、暖機、API範囲、GPU同期、更新時の複製方法、保存復元試験は主測定と同じである。追加の性能計測は33.22秒で完了した。

| 条件 | 初期化ms | 1件評価ms：中央値／p95 | 96件評価ms：中央値／p95 | 1経験更新ms：中央値／p95 |
|---|---:|---:|---:|---:|
| CPU float64 | 42.47 | 11.28／18.49 | 54.02／60.72 | 371.28／395.63 |
| GPU float64 | 20.74 | 4.57／6.38 | 7.79／9.42 | 86.89／90.01 |
| GPU float32 | 10.95 | 4.60／6.63 | 5.31／6.82 | 72.74／75.89 |

100万版でもCPU単独の1件判断は中央値約11msに収まった。ただし更新は約0.37秒となり、526～100kより重い。この容量ではGPU float64の1件・96件バッチ・経験更新のいずれもCPU float64より短かった。100kまでの試験とは異なり、今回の負荷でGPUの利用価値が認められた。

この追加測定中は別の数値実験がCPU worker4本で並行する予定の環境であり、ベンチマークのために他の処理を止めていない。速度は通常の研究作業中の観測値で、主測定時と負荷が等しい保証はない。容量に比例する速度変化の厳密な推定、小さな条件差、GPU64とGPU32の1件評価の差には利用しない。

重みの数値部分はfloat64で8,000,112bytes（約7.63MiB）、float32で4,000,056bytes（約3.81MiB）。CPU測定後のプロセスRSS約648MiB、ピーク約657MiB。GPU測定後はランタイム等を含めRSS約997～1,115MiBで、主測定と同じくNN重み単体のRAMではない。

GPU float64のPyTorch最大確保量は69.67MiB、最大予約量134MiB。float32は最大確保44.07MiB、予約86MiB。GPUテンソルの実デバイスは`cuda:0`。全GPU使用量は測定前3,448MiB、末尾3,559MiBで、他アプリとデスクトップを含むため差分111MiBをNPN単独に帰属させない。上記アロケータ計測と全GPU使用量は別の値である。

同じ16経験をCPU64とGPU64で別々に学習した最大出力差は3.51e-13。GPU64とGPU32の別学習では最大1.07e-5だった。同じGPU64重みをCPUへ復元した試験ではパラメータハッシュが一致し、出力の最大差は5.72e-15。別々の再学習のビット一致と、正本の保存移植は区別する。100万版でfloat32差が小さかったことは、主測定2k版の0.046差を打ち消すものではない。

再現には事前ゲートの実bool値が成功で、数値安定性・別枝保持も成功、ゲート時点で最終評価を未参照であることと、固定追加プロトコルの存在を検証する。条件が揃わなければモデルを割り当てない。従来の`performance.py`は、明示的な追加許可なしの100万呼び出しを引き続き拒否する。

```powershell
& '.\.venv\Scripts\python.exe' experiments/million_performance.py --output-tag million-performance-rerun-1
& '.\.venv\Scripts\python.exe' -m unittest discover -s tests -p test_performance.py -v
```

既存結果を上書きしないため、再計測は新しい名前を使う。ゲート不成立・プロトコル欠落時の拒否、割り当て前の停止、主証拠のハッシュ保持、100万状態のGPU→CPU保存復元を追加テストで検証した。

## 追加の運用確認：毎回起動する評価tool

主結果の後に、実際の `tools/evaluate.py` を新しいCPUプロセスとして起動し、Torch読込み・状態復元・1件評価までを各3回測定した。`reports/cold-tool-performance.json` に原時間を保存した。526版は中央値6.56秒、100万版は5.85秒だった。どちらも同じ保存状態から同じhashを返した。

これはファイルキャッシュを消したディスクの冷起動ではなく、既存CPU環境での新規プロセス起動時間である。他のデスクトップ処理も動いており、容量間の速度順位を示す試験ではない。warm APIの0.63〜11.28msと、毎回Pythonを起動する研究wrapperの待ち時間は明確に違う。本体への将来接続では評価器を管理されたプロセスとして再利用する必要がある。今回、その接続は実装していない。
